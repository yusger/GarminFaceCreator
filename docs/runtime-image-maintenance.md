# 避免增量部署耗尽镜像层数

部署应复用仓库的deploy/Dockerfile.runtime或完整deploy/Dockerfile，从固定.NET运行时基础镜像构建。不要让下一版FROM当前应用镜像：每轮COPY会继续叠加，即使单轮很小也最终出现max depth exceeded。

本轮测试部署已观察到127层，新增一层后无法创建容器。先以保存的上一版本标签恢复应用，再使用当前已成功发布的后端产物与dist，从固定aspnet10.0-noble基底重建，降为10层。后续部署均走相同Dockerfile和新的dotnet publish结果，避免使用旧发布目录。Java、字体依赖由Dockerfile显式安装；SDK、项目数据、日志、私有配置和签名Key继续用原绑定挂载。

仅重建应用服务，保留原生worker、容器资源和鉴权；不清理编译/原生配额账本。每轮发布仍先提交推送并核验远端SHA，再部署与测试，失败必须恢复可运行版本。Git TLS失败通过受信SSH通道执行同一仓库Git推送，并再次读取GitHub实际main SHA核对，不关闭TLS或跳过一致性检查。

本Plan测试环境的两个原生前台配额字段，经用户明确授权暂为100/300，原值10/30。Plan结束仅恢复这两个字段并重建应用加载IOptions；不可恢复整份旧配置覆盖之后的变更。备份私有配置留在运维目录，不提交。worker独立限额和其他资源限制未变，恢复也必须有记录。
